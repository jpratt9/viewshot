# KAN-544: MP4 recordings can't include the tab's audio

Ticket: https://prattsolutions.atlassian.net/browse/KAN-544. It is a To Do Story labelled `viewshot`, with no comments. It is blocked by KAN-221, which is Done.

## What the repo does now

As of `03685aa`:

- **The tab's audio is only requested for WebM.** `startRecording` adds the `audio` constraint only when `audio && format === 'webm'` (`offscreen.js:72-74`). An MP4 start gets video only.
- **Playback and its cleanup don't depend on the format.**
  - When the constraint is there, the tab's sound is played back out through an `AudioContext` (`offscreen.js:95-98`).
  - The context is closed after the file is saved (`offscreen.js:240-245`) and in `teardown` (`offscreen.js:332`).
  - MP4 and WebM already share that stop path.
- **The MP4 MIME type names no audio codec.** `startRecording` calls `pickMime(format)` (`offscreen.js:174`). For MP4 that tries `video/mp4;codecs=avc1`, then plain `video/mp4` (`offscreen.js:252-259`).
- **The popup shows the "Record tab audio" row for WebM only** (`toggleAudio`, `popup.js:94-95`).
- **The worker passes the setting for every format** (`background.js:907`), and the checkbox row is already in `popup.html:35-38`.
- **The README says WebM only.** `README.md:9` says the option adds the tab's sound to WebM recordings.
- **Tests:** `npm test` runs 361 tests, and all pass.
  - Two of them pin the WebM-only behaviour:
    - "a mp4 recording asks for video only, even with audio on", generated by the loop at `tests/capture-errors.test.js:2165-2173`;
    - "the audio row shows only for WebM, and follows the format" (`tests/defaults.test.js:174-183`).
  - The MP4 tests at `tests/capture-errors.test.js:716-735` pin the MIME types of a video-only MP4 (`avc1`, then plain `video/mp4`). This change doesn't touch them.

Choices:

- **Audio for every recording format except GIF**, as the ticket says (`format !== 'gif'`). The row shows for WebM and MP4. GIF has no sound.
- **AAC is named only when audio is being captured.** A video-only MP4 still asks for `video/mp4;codecs=avc1`, so that path and its tests (`tests/capture-errors.test.js:716-735`) stay as they are.
- **Where AAC isn't supported, fall back through the list:** `video/mp4;codecs=avc1`, then `video/mp4`. That is how `pickMime` already falls back from VP9 to VP8 to plain WebM, and from H.264 to plain MP4.
  - With only `avc1` named, Chrome chooses the audio codec itself. Which one it would choose wasn't checked, because Chrome 153 supports AAC and never reaches the fallback.
  - The MP4 option already stays visible in Chrome versions that can't record MP4 (KAN-222).
- **No change to the playback, the stop path or `teardown`.** The `AudioContext` and its `close()` calls don't depend on the format (`offscreen.js:95-98`, `:240-245`, `:332`).
- **No change to the worker or `popup.html`.** `rec-start-offscreen` already carries the setting for every format (`background.js:907`), and the row already exists.
- **The option stays off by default,** as settled in KAN-221.
- **No version bump.**

## Open questions — settled

The plan left no question open, but two points were left undecided or unchecked. Both are settled here, and neither changes the code shipped in `39ecdce`.

1. **What should an MP4 with audio do where AAC isn't supported?** Keep the fallback as shipped: `video/mp4;codecs=avc1`, then `video/mp4`, with Chrome choosing the audio codec.
   - `pickMime` already falls back through a list for both formats: VP9, VP8, plain WebM; H.264, plain MP4. And KAN-222 leaves MP4 to the existing error path where Chrome can't record it at all.
   - The ticket asks for the tab's audio in MP4 and for AAC. AAC is what Chrome 153 uses on macOS, where QuickTime Player runs.
   - With the option on, a recording that keeps its sound in another codec is closer to what was asked for than one that silently drops it.
2. **Listening in QuickTime Player** (step 4 left this for John).
   - The MP4 recorded in step 4 was decoded with `afconvert`, which goes through AudioToolbox, the same AAC decoder QuickTime Player uses.
   - It decoded to 3.62 s of 44.1 kHz stereo at -55.1 dB mean. Within a narrow 440 Hz band the mean was -55.2 dB, and with 440 Hz notched out it was -90.3 dB. The audio track is the page's tone and nothing else.
